# 胡了卜 Cocos 正式游戏 v1 产品与技术设计

- 任务：T241
- 负责人：Lee
- 日期：2026-07-10
- 状态：方向已确认，书面规格待用户审阅
- 正式运行时：Cocos Creator 3.8.8
- 首发平台：移动端竖屏 Web，桌面浏览器以竖屏游戏画布承载
- 目标版本：一个可以从标题页完整玩到结算、可失败恢复、可重复开局的正式章节

## 1. 结论先行

胡了卜不再以“Web demo 和 Cocos 功能追平”为目标。v1 从现在起执行以下不可逆的产品约束：

1. Cocos 是唯一正式游戏运行时，也是玩法、流程、内容和表现的唯一真相源。
2. Web 只负责加载、全屏、可见性、站点导航和可选的事件转发，不再实现游戏规则与关卡。
3. 先交付一个 20–30 分钟的完整章节，不把无尽、高阶、每日、成就和账号同步塞进首发阻塞路径。
4. 先把现有大控制器拆成可测试的会话核心、流程状态机、内容仓库、存档服务和 Cocos 表现层，再继续扩内容。
5. UI 和音频是 v1 功能，不是发布前的装饰补丁。没有正式入口、清晰反馈、声音、失败恢复和发布门禁，就不算可上线。

这条路线保留现有 Cocos 已经验证过的玩法资产，但停止继续堆功能。所有后续工作围绕一个纵向完整、可验收的游戏版本展开。

## 2. 当前基线与问题判断

### 2.1 已经具备的能力

- Cocos 工程已有密集牌山、遮挡点击、主槽/备用槽、牌河、记牌器和三类工具。
- 已有手动 `吃 / 碰 / 杠 / 补杠 / 胡`、多候选组合、奖励、事件、Boss、多个 run mode、本地成长和 active run 存档基础。
- Cocos TypeScript 检查通过，共享静态测试当前 31 项通过。
- 2026-07-10 fresh `web-mobile` 非 debug 构建实际生成了 `index.html` 和完整发布目录。

### 2.2 不能直接上线的原因

| 现状 | 证据 | 上线风险 |
| --- | --- | --- |
| 核心 Controller 职责过多 | `GameSceneController.ts` 为 3501 行，同时处理 UI、规则 fallback、流程、存档和账号桥接 | 修改一个界面可能破坏规则或恢复流程，无法稳定迭代 |
| 规则存在双路径 | Controller 的 `refreshPlayableScene()`、`findComboCandidate()`、`findHuCandidate()` 等 fallback 与 `HulebuRuntimeState` 并存 | 同一操作在不同初始化状态下可能得到不同结果 |
| 内容没有唯一真相源 | Cocos 在 `HulebuLevelConfig.ts` 中维护大段硬编码，Web/shared 另有 JSON 与规则 | Web demo 与正式游戏会继续漂移，平衡和修复无法复用 |
| UI 仍是程序化壳 | 资源下只有一份 `.scene`，没有正式 Prefab/Animation/Atlas 结构 | 组件状态、过场、布局和美术替换成本持续上升 |
| 没有音频系统 | Cocos 资源中没有 mp3/wav/ogg/m4a，也没有 AudioSource/AudioClip 播放逻辑 | 操作缺少重量、危险与奖励反馈，成品感不足 |
| 包体与模块未治理 | Cocos assets 约 127 MB，v6 UI 约 9.7 MB，构建包含大量暂未使用的引擎模块 | 首屏加载、移动端内存和发布体积不可控 |
| 构建判定不可靠 | 日志显示 `build Task (web-mobile) Finished`，产物完整，但 Cocos CLI 返回 36 | CI 可能把成功当失败，也可能在未来把不完整产物误放行 |
| 产品入口不稳定 | 新档直接进入教程/局内，主菜单、设置、继续和错误恢复没有统一 App Flow | 玩家无法确认当前状态，也缺少完整开局与退出路径 |

### 2.3 判断

当前不是“缺几个 UI 和音效”的小修问题，而是产品闭环和运行时边界没有收口。继续补单点功能会让代码更像半成品。正确做法是保留已验证能力，冻结新增模式，围绕一个完整章节重建可发布骨架。

## 3. v1 产品合同

### 3.1 玩家承诺

玩家第一次打开胡了卜后，90 秒内理解“翻开自由牌、放入 8 格主槽、手动发动吃碰杠胡、用有限工具化解危局”。一次完整章节持续 20–30 分钟，包含学习、构筑选择、压力升级、Boss 和明确结算。

### 3.2 核心幻想与操作动词

- 核心幻想：攀登一座会不断重组的麻将牌山，在槽位压力中组织牌型，以手动发动的麻将组合破局。
- 主要动词：观察、翻牌、入槽、选候选、吃、碰、杠、胡、用工具、选奖励、承担事件结果。
- 决策焦点：现在消掉稳定组合，还是等待更高价值的杠/胡；保留工具，还是在满槽前主动止损。

### 3.3 v1 明确包含

- 标题页：`新游戏 / 继续游戏 / 设置`。
- 首次引导：融入前两场遭遇，不使用独立长说明页。
- 一个章节，10 个节点：7 个普通/教学牌局、1 个精英牌局、1 个事件、1 个 Boss。
- 三次奖励三选一，合计 12 张可抽取奖励卡。
- 固定 8 格主槽、1 格备用救场槽、牌河和记牌器。
- 手动 `吃 / 碰 / 杠 / 补杠 / 胡`，多候选时必须由玩家选择。
- 三个工具：洗牌、撤回、弃牌；每个工具都具有数量、禁用态、成功和失败反馈。
- 章节内检查点、本地继续、失败结算、重新挑战和完整通关结算。
- 3 首 BGM、18 类核心 SFX、主音量/音乐/音效三组设置。
- 移动端竖屏和桌面浏览器发布构建、性能门槛、错误页和基础事件埋点。

### 3.4 v1 明确不包含

- 无尽牌山、高阶周目、每日牌局、成就图鉴的正式入口。
- 开局流派六选一、复杂局外升级树、体力和付费。
- 账号跨设备同步、排行榜、多人玩法。
- 完整麻将听牌、番型、算番和真实麻将流程。
- 商业级人物 cut-in。v1 用书法操作字、牌面合拢、粒子和音效完成大操作演出。
- Cocos 与 Web demo 的功能对等。Web demo 保留为历史参考，不进入生产导航和回归范围。

### 3.5 首发后的可见状态

已有的无尽、高阶、每日、成就和复杂长期成长代码不作为 v1 删除目标，但必须从正式入口隐藏，并通过 feature flags 与 v1 流程隔离。它们只有在核心版本稳定、各自获得独立设计和验收后才能重新开放。

## 4. 完整玩家旅程

```text
Boot
  -> 资源/配置/存档校验
  -> 标题页
      -> 新游戏 -> 遭遇 1-2 内嵌教学
      -> 继续游戏 -> 最近稳定存档点
      -> 设置 -> 音量/震动/减弱动效
  -> 章节节点 1-3
  -> 奖励三选一 + 检查点 A
  -> 章节节点 4-6
  -> 事件选择 + 奖励三选一 + 检查点 B
  -> 精英节点 7-8
  -> 奖励三选一 + 检查点 C
  -> Boss
  -> 章节结算
      -> 再来一局 / 返回标题
```

### 4.1 首次 90 秒

1. 标题页只突出一个主按钮 `开始攀山`；有存档时主按钮改为 `继续攀山`，`新游戏`进入二级确认。
2. 第一场仅要求点击高亮的自由牌，展示入槽动画和 8 格容量。
3. 当第一组合法组合出现时，组合按钮发光但不自动执行；玩家点击后完成第一次 `碰`。
4. 第二场引入多候选和牌山遮挡，玩家选择一组 `吃`。
5. 第二场结尾展示一次危险槽位和免费教学用撤回，不让首次教学因误触直接失败。

### 4.2 常规局内循环

1. 观察牌山自由牌、主槽、余牌和当前目标。
2. 点击自由牌，牌进入主槽；动画期间所有会改变牌局的输入锁定。
3. 会话核心计算组合候选、危险状态、Boss 目标和可用工具。
4. 玩家手动发动组合或继续翻牌；多个候选先进入候选选择。
5. 组合结算积分、效果和目标进度，再回到可输入状态。
6. 清空牌山且完成目标则胜利；主槽满且没有组合/救场出口则进入危局判定。

### 4.3 失败与恢复

- 危局顺序固定为：组合检测 -> 备用槽 -> 可用救场工具 -> 教学保护 -> 失败。
- 失败页必须显示：失败原因、最后 5 次关键操作、当前构筑、距下一检查点、`从检查点重试 / 重新开始章节 / 返回标题`。
- 章节在三次奖励后保存检查点。检查点保存当时的奖励、分数、工具和章节位置。
- 局中在每次完整结算后的稳定阶段保存 active run。动画、候选半选中和弹层过渡态不直接持久化。
- 局中存档无效时先恢复最近检查点；检查点也无效时保留设置与通关记录，回到标题页并给出可理解提示。

### 4.4 通关与重玩

- 结算页展示总分、吃碰杠胡次数、工具使用、失败重试、Boss 目标和本局奖励路线。
- 首通记录 `chapter01Cleared` 并解锁 `再来一局`。重玩使用同一内容池和不同合法 seed，不新增第二套模式入口。
- v1 只保存最高分、最短通关时间、最佳胡次数三项重玩目标，避免在首发前扩建完整成就系统。

## 5. 章节内容设计

### 5.1 十节点节奏

| 节点 | 类型 | 教学/压力 | 目标时长 | 退出条件 |
| --- | --- | --- | --- | --- |
| 1 | 教学牌局 | 自由牌、入槽、手动碰 | 2 分钟 | 完成一次碰并清台 |
| 2 | 教学牌局 | 遮挡、吃、多候选 | 2–3 分钟 | 玩家主动选候选并清台 |
| 3 | 普通牌局 | 杠与记牌器 | 2–3 分钟 | 完成指定组合或清台 |
| 4 | 普通牌局 | 8 格压力、备用槽 | 2–3 分钟 | 在不耗尽备用槽时清台 |
| 5 | 普通牌局 | 胡 `3 + 3 + 2` | 3 分钟 | 至少完成一次胡 |
| 6 | 普通牌局 | 工具取舍 | 2–3 分钟 | 清台，记录工具消耗 |
| 7 | 事件 | 安全小收益 / 风险大收益 | 1 分钟 | 二选一并立即应用 |
| 8 | 精英牌局 | 两类目标并行、低容错 | 3–4 分钟 | 完成双目标并清台 |
| 9 | 普通牌局 | Boss 前构筑检验 | 2–3 分钟 | 清台并进入最终奖励 |
| 10 | Boss | 阶段目标、危险提示、专属演出 | 4–5 分钟 | 完成目标并清空牌山 |

奖励节点位于 3、6、9 之后，选完奖励立即写检查点。事件节点不单独发奖励，避免章节后半选择过密。

### 5.2 奖励池

12 张奖励分为四组，每组 3 张：

- 组合强化：吃后返分、碰后保护、杠后补牌。
- 槽位救场：备用槽强化、首次满槽保护、死孤张转河。
- 工具强化：洗牌增益、撤回返还、弃牌附带得分。
- 信息与节奏：记牌器强化、顶层透视、Boss 目标预告。

同一奖励不能在同一次三选一中重复。选择结果由 seed 决定并可在重放日志中复现。v1 不引入稀有度、装备槽和复杂冲突表。

### 5.3 Boss 规则

- Boss 只有三项同时可读的目标：完成 1 次杠、完成 1 次胡、清空牌山。
- 目标始终固定在顶部 HUD，完成后明确打勾，不用长文案轮播。
- Boss 进入、目标完成和最终清台分别使用不同音频/动效层级。
- Boss 牌山仍必须由同一生成器和同一规则核心产生，不允许用脚本直接判胜。

### 5.4 可解性原则

- 所有关卡使用固定 seed 集合进入自动验证；每个正式 seed 至少存在一条不依赖付费或随机重抽的合法通路。
- 可解性保证初始存在通路，不保证任意玩家操作都可挽回。
- 生成器必须输出可追踪的组合包来源、遮挡图和目标包，便于失败复盘和自动检测。

## 6. 目标架构

### 6.1 总体边界

```text
Web Host
  loading / fullscreen / visibility / analytics bridge
                      |
                      v
Cocos App Flow
  boot / title / loading / chapter / result / settings
                      |
                      v
Game Coordinator <-> Run State Machine <-> Game Session
       |                    |                  |
       v                    v                  v
 ContentRepository      SaveService       Rules + Generator
       |
       v
Cocos Presentation
  scenes / prefabs / binders / animation / audio cues
```

### 6.2 唯一真相源

- 玩法规则的唯一源码位于 Cocos 工程内不依赖 `cc` 的纯 TypeScript `domain/`。
- 关卡、奖励、教程和音频映射的唯一内容源是带版本的 Cocos resources JSON。
- Cocos 节点、Sprite、Tween、AudioSource 和浏览器 API 只能出现在 adapter/presentation 层。
- Web demo 不再消费或修改正式内容，也不要求与正式版回归一致。

选择“纯 TypeScript domain 位于 Cocos 工程内”是因为 Creator 已经证明无法可靠打包工程外相对 import。测试从仓库侧直接导入纯模块，避免再复制一份 generator 或规则。

### 6.3 模块职责

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `GameSession` | 牌山、槽位、组合、工具、积分、目标、危险判定 | Scene、动画、存档、网络 |
| `RunStateMachine` | 遭遇、奖励、事件、Boss、结算和合法 phase 转移 | 牌型算法、节点渲染 |
| `GameCoordinator` | 接收命令、驱动 session/run、发布 snapshot 与 domain events | 直接创建 Cocos 节点 |
| `ContentRepository` | 加载、校验、索引版本化内容 | 在运行时修补坏数据 |
| `SaveService` | 本地快照、版本迁移、检查点、坏档隔离 | 保存 renderer 对象 |
| `AudioService` | 音频总线、解锁、播放、防重、后台暂停 | 决定游戏规则 |
| `AppFlowController` | Boot、Title、Game、Result、Settings 场景导航 | 牌局内部状态 |
| Cocos Presentation | Prefab、布局、输入映射、动画、粒子、文本与音效消费 | 重算规则或偷偷改状态 |
| Web Host Adapter | 加载、全屏、可见性、错误和匿名事件转发 | 规则、存档合并、关卡 UI |

### 6.4 命令、快照和事件

表现层只提交命令：

```ts
type GameCommand =
  | { type: "tile.select"; tileId: string }
  | { type: "combo.execute"; combo: "chi" | "peng" | "gang" | "bugang" | "hu" }
  | { type: "combo.choose"; candidateId: string }
  | { type: "tool.use"; tool: "shuffle" | "undo" | "discard" }
  | { type: "reward.choose"; rewardId: string }
  | { type: "event.choose"; optionId: string }
  | { type: "flow.pause" }
  | { type: "flow.resume" };
```

核心返回不可变 `GameSnapshot` 和领域事件。UI 只绑定 snapshot；动画、声音、震动和埋点消费事件。任何 Cocos Binder 都不能自行判断“是否能胡”或直接改分数。

### 6.5 状态机

App Flow：

```text
boot -> title -> loading -> chapter -> result
                 |            |
                 v            v
               error        pause
```

Run Flow：

```text
encounterIntro
  -> playing.idle
  -> playing.tileEntering
  -> playing.comboChoosing
  -> playing.resolving
  -> playing.dangerCheck
  -> encounterCleared
  -> rewardChoice | eventChoice | bossIntro | settlement
  -> failed
```

只有 `playing.idle`、选择弹层、节点入口、检查点和结算是可持久化稳定态。恢复后不重播已结算的奖励、音效或计分事件。

### 6.6 渐进迁移方式

不进行一次性推倒重写。采用绞杀式迁移：

1. 先给现有行为补特征测试与固定 seed 快照。
2. 建立 Coordinator 和命令入口，让旧 Controller 先通过新入口工作。
3. 逐项把规则、流程、存档、音频和 UI 创建迁出 Controller。
4. 每迁出一项就删除对应 fallback，并用测试证明只有一条路径。
5. 当 Controller 只负责场景装配和转发后，再拆成更小的 Scene Controller/Binder。

### 6.7 现有能力取舍表

| 分类 | 内容 | 处理方式 |
| --- | --- | --- |
| 保留并加保护 | 麻将牌资源、遮挡图、8 格主槽、备用槽、牌河、记牌器、三工具、手动组合语义 | 先用固定 seed 与特征测试锁定，再迁入唯一 domain 路径 |
| 重建边界 | App Flow、Run Flow、内容仓库、存档、音频、Scene/Prefab UI、发布脚本 | 以新接口逐项替换旧 Controller 职责 |
| 首发隐藏 | 无尽、高阶、每日、成就、复杂局外成长、账号同步 | feature flag 默认关闭，不进入标题页和生产回归 |
| 验证后删除 | Controller 内规则 fallback、Web demo 生产入口、重复 generator、动态整页 UI 创建、过时“工程壳”文档 | 新路径通过等价测试后同批删除，避免永久双轨 |

迁移不是按 Web 页面逐行复刻。每项旧功能先进入 `保留 / 重建 / 隐藏 / 删除` 四选一清单，未分类的功能不能进入 v1。

## 7. 内容与数据设计

### 7.1 正式内容目录

```text
assets/resources/hulebu/
  content/
    manifest.json
    chapter-01.json
    encounters.json
    rewards.json
    events.json
    tutorial.json
  audio/
    audio-manifest.json
  ui/
    ui-manifest.json
```

`manifest.json` 固定包含 `contentVersion`、兼容的 `saveSchemaVersion`、章节入口、资源组和构建版本。ContentRepository 在 Boot 阶段一次性校验引用、ID 唯一性、Boss 目标、奖励数量和 seed 集合，错误时进入可重试错误页，不带坏配置继续游戏。

### 7.2 内容版本原则

- 正式 ID 一旦进入存档不得复用为另一含义。
- 平衡数值可以改，但章节结构变更必须提升 `contentVersion`。
- 内容加载完成后转为只读对象；运行时效果存入 session，不回写配置。
- 所有面向玩家的中文文案使用 copy key，不散落在 Controller 中。v1 只交付 `zh-CN`，但结构不阻断后续语言包。

## 8. 存档与宿主集成

### 8.1 本地存档

v1 采用 local-first，共三类数据：

- `settings`：音量、震动、减弱动效、教程提示。
- `profile`：教程完成、章节通关、最高分、最短时间、最佳胡次数。
- `activeRun`：schema 版本、内容版本、seed、当前稳定 phase、session snapshot、章节奖励和最近检查点。

存档采用临时键写入、读回校验、再替换正式键的原子流程。每个 schema 版本有显式迁移函数。无法迁移的坏档转存到带时间戳的 quarantine key，不静默覆盖。

### 8.2 账号同步

现有账号桥接只能放在 `ProgressPort` 适配器之后，并由 feature flag 关闭。v1 发布不依赖登录、接口和冲突合并。后续启用时，服务端只能同步 profile 和稳定检查点，不直接操作 Cocos 对象。

### 8.3 Web Host 契约

Web 与 Cocos 只交换以下消息：`game.ready`、`game.error`、`game.pause`、`game.resume`、`game.fullscreen`、`game.analytics`。消息带 `protocolVersion`，无效来源和未知消息被忽略。Host 不读写具体牌局状态。

## 9. 正式 UI 设计

### 9.1 视觉方向

- 主题：山路、漆木牌桌、玉质麻将、宣纸纹理和克制的金红书法反馈。
- 主色关系：墨黑负责文字，象牙白负责牌面，青玉绿负责牌桌，漆红负责危险与关键操作，金色只用于奖励和完成态。
- 不使用整页米色、单一暗蓝或满屏金色。UI 不能看起来像后台卡片面板。
- 大操作采用书法字、牌面合拢、局部火花/纸屑和屏幕震动；不使用低质量人物占位 cut-in。

### 9.2 场景与 Prefab

正式工程至少拆为：

- Scene：`Boot`、`Title`、`Game`、`Result`。
- Prefab：`Hud`、`Tile`、`MainSlot`、`ReserveSlot`、`ComboBar`、`ToolDock`、`TileCounter`、`ObjectiveStrip`、`ModalFrame`、`ComboChoice`、`RewardCard`、`EventChoice`、`PauseMenu`、`SettingsPanel`、`Toast`。
- 动画 Clip：入槽、被压提示、组合结算、危局、奖励出现、Boss 进入、胜利、失败。

运行时可以池化 Tile 和短命 FX，但不能继续在一个 Controller 内用数百行代码即时拼完整页面。

### 9.3 画布与响应式

- 设计基准为 390x844 竖屏，使用安全区，不让刘海、Home Indicator 和浏览器栏遮挡操作。
- 手机竖屏为完整交互模式；横屏显示轻量旋转提示并暂停规则输入。
- 桌面浏览器保持竖屏游戏比例，画布最大 540x960，居中显示，不横向拉伸牌桌。
- 关键点击目标换算到 CSS 尺寸后不小于 44x44；禁用态同时使用亮度、描边和图标变化，不能只靠颜色。
- 常态 HUD 只保留顶部目标/分数、左上记牌器、右侧工具和底部组合/槽位，中间牌山不被说明文本覆盖。

### 9.4 页面清单

| 页面/层 | 必须包含 | 验收重点 |
| --- | --- | --- |
| Boot/Loading | 品牌、真实进度、重试 | 不是假进度；配置/资源错误可恢复 |
| Title | 继续/新游戏、设置、版本 | 3 秒内知道如何开始 |
| Game HUD | 关卡、目标、分数、记牌器、工具、组合、槽位 | 牌山是第一视觉焦点 |
| Tutorial | 指向目标的遮罩和一步一提示 | 不用长说明卡挡住牌桌 |
| Combo Choice | 候选真实小牌面、取消 | 不替玩家默认选择 |
| Reward | 三张卡、差异、确认反馈 | 文案短，效果在选择前可理解 |
| Event | 二选一、风险/收益 | 风险不靠模糊措辞隐藏 |
| Boss Intro | Boss 名称、三目标、跳过 | 不超过 3 秒，重复游玩可跳过 |
| Pause/Settings | 继续、音频、动效、重开、返回标题 | 暂停时规则输入完全关闭 |
| Failure | 原因、关键操作、构筑、三个去向 | 不只显示“失败” |
| Result | 数据复盘、首通、再来一局 | 能完成闭环并再次开始 |

### 9.5 资产差距

现有 v6 资源只作为候选库，逐张经过透明边缘、分辨率、九宫格拉伸和状态完整性检查后复用。v1 必须新增或补齐：

- 正式标题 Logo、标题背景、章节背景、Boss 背景。
- `胡` 正式按钮，以及吃/碰/杠/补杠/胡的 normal/pressed/disabled/active 状态。
- 三个工具图标与空次数、禁用、可用状态。
- 主槽、备用槽、牌河、记牌器、目标条和中心弹层九宫格。
- 12 张奖励卡的图标与统一卡框，事件和 Boss 图标。
- 组合印章、危险提示、胜利/失败、奖励获得的 FX 图集。
- 可商用中文字体及许可证记录。

每项资产进入 `ui-manifest.json`，代码只使用稳定 key，不把磁盘文件名当公开 API。

## 10. 音频与动效

### 10.1 音频清单

- BGM 3 首：标题/山路、普通牌局、Boss。每首提供无明显断点的循环段。
- Stinger 4 个：遭遇开始、奖励、胜利、失败。
- 核心 SFX 18 类：按钮确认、返回、牌可选、牌被压、入槽、候选出现、吃、碰、杠、补杠、胡、洗牌、撤回、弃牌、槽位危险、目标完成、奖励选择、Boss 警告。

源文件保留无损母带；发布文件按浏览器兼容性输出压缩版本。所有外部音频必须记录来源、作者、许可证、修改方式和项目可用范围。

### 10.2 AudioService

- 三条总线：master、music、sfx；音量范围 0–100，保存到 settings。
- 第一次玩家手势统一解锁 WebAudio；解锁前的 BGM 请求只排队，不反复创建 AudioSource。
- 页面隐藏时淡出并暂停，恢复可见后按当前 App/Run phase 恢复正确曲目。
- 高频入槽音设置并发上限和最小间隔，避免连续点击爆音。
- 音频失败不阻断规则；正式构建的 manifest 缺失则在发布校验中失败。

### 10.3 动效层级

- 轻：按钮、翻牌、入槽，100–220 ms。
- 中：吃/碰、工具、奖励选择，250–500 ms。
- 重：杠/补杠/胡、Boss 目标、胜利，500–1000 ms。
- 输入锁定只覆盖真正改变状态的结算段，不能让华丽动画拖慢常规翻牌。
- `减弱动效` 开启后移除震屏、长位移和多段粒子，但保留状态反馈。

## 11. 构建、性能与发布

### 11.1 构建基线

- 锁定 Cocos Creator 3.8.8 和 Node 版本，发布目标固定为非 debug `web-mobile`。
- 新增受控构建包装器，校验 Creator 日志、`index.html`、settings、入口脚本、资源 manifest 和版本文件。
- 当前 Creator CLI 的退出码 36 单独建立修复任务。包装器在原因查清前不得只看退出码，也不得仅凭 Finished 字符串放行，必须同时验证产物完整性并执行本地 HTTP smoke test。
- 发布目录由脚本生成，不手工复制进 Web public。每次产物写入 commit SHA、contentVersion、saveSchemaVersion 和构建时间。
- 生产产物发布到不可变路径 `/games/hulebu/runtime/<buildId>/`；宿主只读取 `/games/hulebu/runtime/current.json` 指向的版本。回滚通过切换该指针完成，不覆盖旧构建。

### 11.2 体积与加载预算

- 首次可交互所需压缩下载不超过 15 MB。
- 完整第一章节压缩下载不超过 35 MB。
- BGM、Boss 与结算资源按资源组延迟加载，不让全部 127 MB assets 进入首屏依赖。
- 移除未使用的 Physics、Spine、Video、WebView 等引擎模块或证明其运行时必要性。
- 所有超过 512 KB 的位图进入资源审计；重复图、整张概念图和未引用版本不得进入发布包。

### 11.3 运行预算

- 桌面宽带从导航到可操作标题页不超过 4 秒；模拟 Fast 4G 的目标移动设备不超过 8 秒。
- 目标设备常规牌局中位帧率不低于 55 FPS，1% low 不低于 30 FPS。
- 点击到首个视觉/声音反馈不超过 100 ms。
- 目标 Android 设备峰值标签页内存低于 300 MB；连续重试三次后内存不持续上升。
- 切后台 60 秒再恢复，音乐、计时、输入锁和存档状态保持一致。

### 11.4 首发兼容矩阵

- iPhone 12 Safari、iPhone SE 第二代尺寸 Safari。
- 6 GB 内存的中端 Android Chrome。
- Windows Chrome/Edge、macOS Safari/Chrome 最近两个稳定大版本。
- 390x844、360x800、412x915、1280x720、1440x900 五组视口截图。

首发只支持竖屏交互。横屏、浏览器缩放、失焦、刷新、网络离线和音频被系统中断都必须有确定行为。

### 11.5 可观测性

匿名事件最小集：`boot_ready`、`boot_error`、`tutorial_step`、`encounter_start`、`encounter_end`、`combo_execute`、`tool_use`、`run_fail`、`run_resume`、`chapter_complete`。不采集牌桌截图、昵称或个人信息。开发构建提供 seed、phase、FPS、内存趋势和最近命令的调试面板，生产构建默认关闭。

## 12. 测试策略

### 12.1 自动化测试金字塔

1. Domain 单元测试：吃碰杠补杠胡、槽位、备用槽、工具、Boss 目标、危局顺序。
2. State machine 测试：所有合法/非法 phase 转移、暂停恢复、候选选择、奖励和结算只触发一次。
3. 内容契约测试：ID、引用、奖励数量、十节点顺序、正式 seed、资源 key 和 copy key。
4. 生成器与可解性测试：100 个候选 seed 自动跑启发式求解，正式 seed 全部通过。
5. 存档测试：当前 schema round-trip、每个旧 schema 迁移、坏档隔离、检查点 fallback。
6. Cocos 集成 smoke：Boot -> Title -> New -> 第一次组合 -> Pause -> Resume -> Save -> Reload。
7. 构建 E2E：通过 HTTP 服务真实 production build，完成桌面和移动端截图、点击、音频解锁、后台恢复。

### 12.2 手工体验测试

- 新玩家 5 人不看说明，记录 90 秒内是否会翻牌、是否理解手动组合、首次失败原因是否清楚。
- 内部完整通关 20 局，记录每节点时长、失败位置、工具使用、奖励选择和 Boss 目标完成率。
- 每个目标设备至少完成 1 次从标题到结算的全流程。
- 耳机和外放分别检查音量、峰值、循环断点、后台恢复和同时播放上限。

### 12.3 发布缺陷门槛

- P0：崩溃、白屏、坏档、无法通关、规则错误、支付/隐私问题。必须为 0。
- P1：流程阻断、关键按钮失效、严重遮挡、音频失控、明显掉帧。必须为 0。
- P2：非关键视觉瑕疵、低频文案或轻微动效问题。允许带明确 owner 和版本安排上线，但总数不超过 5。
- 控制台未处理异常为 0，生产资源 404 为 0，调试文案/占位图/开发按钮为 0。

## 13. 分阶段路线图

### M0：止血与可重复基线，2–3 人日

产物：冻结 Web demo；记录当前 golden screenshots、seed 和行为；收口 T239/T240 并发；建立 production build 包装器、版本文件和 HTTP smoke；列出 v1 keep/hide/delete 清单。

退出标准：任何人可从干净环境生成并启动同一 production build；构建异常被清晰报告；v1 之外功能无法从正式入口进入。

### M1：核心边界与状态机，5–7 人日

产物：纯 TypeScript `GameSession`、`RunStateMachine`、命令/快照/事件契约、ContentRepository、SaveService；现有 Controller 通过 Coordinator 驱动；删除一条规则 fallback。

退出标准：规则和 phase 测试通过；同一 seed 在无渲染环境可复现；刷新后恢复到稳定 phase；Controller 不再直接判定组合和得分。

### M2：三节点纵切，5–7 人日

产物：Boot、Title、Game、Result 场景；前两场教学、一个 mini Boss、一次奖励、失败和继续；第一版 Prefab 和临时但完整的音频链路。

退出标准：新玩家能从标题完成 8–12 分钟小章节；桌面/手机生产构建全流程可玩；没有调试入口和流程死路。

### M3：完整十节点章节，5–7 人日

产物：十节点内容、12 奖励、事件、精英、正式 Boss、三检查点、确定性 seed 与平衡记录。

退出标准：内部 20 局完整通关，无不可解正式 seed；中位章节时长 20–30 分钟；各节点失败率没有异常尖峰。

### M4：正式 UI、音频与反馈，6–9 人日

产物：正式 UI 资产、Prefab 状态、动效 Clip、3 BGM、18 SFX、设置、减弱动效、许可证清单；清理所有概念图和占位资源。

退出标准：390x844 和桌面截图符合视觉层级；所有操作有可区分反馈；关闭声音后无泄漏；没有缺状态按钮和临时文字。

### M5：性能、QA 与上线，4–6 人日

产物：资源分组和引擎裁剪、设备矩阵、存档迁移、后台恢复、埋点、发布清单、回滚包和版本说明。

退出标准：满足体积、加载、帧率、内存和缺陷门槛；每个目标设备完成全流程；同一版本可部署、验证和回滚。

### 13.1 总体投入

- 总投入与 M0–M5 一致，为 27–39 人日。
- 工程与自动化测试：约 20–27 人日。
- UI、动效和音频资产：约 4–7 人日，可与 M2/M3 的工程工作并行。
- 真机 QA、调优和发布：约 3–5 人日，部分已计入 M5。
- 单人主开发配合兼职 UI/音频，建议预留 5–7 个自然周和 20% 风险缓冲。

该估算以复用现有麻将牌、牌山、规则和 UI 候选资产为前提。如果推翻牌山玩法或要求商业级人物演出，应作为新范围重新估算。

## 14. 实施任务拆分原则

书面规格确认后，代码级实施计划按以下批次生成，每批可独立评审与回退：

1. 发布基线、Web demo 冻结和 build wrapper。
2. Domain 特征测试、GameSession 和唯一规则路径。
3. RunStateMachine、Coordinator 和 App Flow。
4. ContentRepository、十节点 schema 和正式 seed 校验。
5. SaveService、检查点、迁移与坏档恢复。
6. Cocos Scene/Prefab UI 骨架和响应式安全区。
7. 三节点纵切与浏览器 E2E。
8. 完整章节内容与平衡。
9. 正式 UI 资产、动效和 AudioService。
10. 包体、性能、兼容、埋点、发布与回滚。

每批必须先写失败测试或可复现检查，再实现最小改动，最后运行 scoped tests、Cocos typecheck、production build 和对应截图/真机检查。不得以“整个大控制器最后一起测”作为验收方式。

## 15. 上线 Definition of Done

只有同时满足以下条件，胡了卜 v1 才可标记为“完整可玩并可上线”：

- 玩家从标题页开始，不看外部说明即可完成教学、十节点、Boss 和结算。
- 章节时长处于 20–30 分钟区间，失败原因可理解，继续/检查点可靠。
- 所有正式规则只有一个实现路径；Web demo 不再参与生产运行。
- 所有正式页面使用 Scene/Prefab 和稳定资源 key，不依赖 Controller 动态拼完整 UI。
- UI、动效、3 BGM、18 SFX、设置和许可证清单完整，无开发占位。
- production build 可重复生成，通过本地 HTTP smoke、桌面/移动端 E2E 和目标设备全流程。
- 正式 seed 可解，存档可迁移，坏档有 fallback，刷新/后台/横竖屏行为确定。
- 满足体积、加载、帧率、内存和 P0/P1 缺陷门槛。
- 有版本清单、部署记录、回滚包和发布后关键事件监测。

## 16. 风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| Controller 拆分引发回归 | 同一 seed 新旧结果不同 | 先做特征测试和双跑比对，逐职责迁移，不一次重写 |
| 现有功能诱发范围膨胀 | M2 前继续开放新模式入口 | feature flag 隐藏，所有新模式需求进入独立任务池 |
| Cocos 外部模块再次打包失败 | Creator Preview 找不到工程外 TS | domain 放在 Cocos 工程内且无 `cc` 依赖，仓库测试直接导入 |
| 正式 UI 到得太晚 | M3 仍用无状态占位按钮 | M2 即建立最终 Prefab 结构，M4 只替换资产和精修动效 |
| 音频授权不清 | 资源只有文件没有来源 | audio manifest 强制许可证字段，构建校验缺字段即失败 |
| 包体继续膨胀 | 未引用概念图进入 resources | 资源引用报告、组加载、512 KB 图片审计、引擎模块裁剪 |
| 坏档阻断开局 | schema 改动后 title 白屏 | 原子写入、迁移测试、quarantine、检查点 fallback |
| 构建退出码误判 | 产物完整但 CI 红，或日志 Finished 但文件缺失 | 退出码调查与产物校验并行，HTTP smoke 为最终门禁 |

## 17. 已锁定决策

- 引擎锁定 Cocos Creator 3.8.8，不迁移 Phaser/Three.js。
- 竖屏 390x844 为首要体验，桌面不改为横版布局。
- 正式游戏内 UI 全部使用 Cocos Scene/Prefab；DOM 只做 Web 宿主和错误兜底。
- v1 使用一个均衡起始配置，通过三次局内奖励形成构筑，不提供开局六流派选择。
- v1 本地可玩、无需登录、无付费、无体力。
- v1 只交付简体中文，但文案进入 key 化内容层。
- v1 不做人物 cut-in，优先把牌面、书法字、粒子、震动和声音做完整。
- 现有 Web demo 冻结；迁移以“行为取舍表”为准，不按文件逐行追平。
