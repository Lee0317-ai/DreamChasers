## 1. 目标定位

这次平台治理不是为了扩一个更大的 AI 后台，而是为了建立一套所有 AI 产品线都必须经过的统一口径，让账号中心、AI Gateway 和产品接线不再各写各的。

第一阶段优先目标不是“尽快堆更多模型能力”，而是先把平台治理打稳：

- 用户能看清现在能用什么 AI 能力、这些能力靠什么来源运行、最近调用出了什么问题。
- 平台内部统一管理模型目录、provider 启用条件、积分扣减和请求日志。
- 新产品接线前必须满足统一准入标准，不允许每条产品线自己发明一套模型、扣费和错误处理逻辑。

## 2. 边界与不做

第一阶段不做：

- 复杂多 provider 自动路由。
- 用户 provider key 持久化。
- 真正的运维后台、告警中心或异步任务平台。
- 支付、订阅、Key Vault、KMS、队列、工作流编排。
- 让 PDF 工具箱、AI 修图、TimePick 各自成长为独立 AI 平台。

核心取舍是先把平台做成“可解释、可治理、可扩展”，再逐步增加真实 provider 数量和高阶产品能力。

## 3. 平台职责边界

### 3.1 账号中心

账号中心负责解释和治理展示，不负责真正执行模型调用。

它需要回答：

- 现在有哪些 AI 能力和模型可用。
- 每种能力默认支持哪些 credential source。
- 当前平台积分如何变化。
- 最近哪些调用成功、哪些失败、失败属于哪一类原因。

账号中心是第一阶段的控制面和观察面，不是执行面，也不是复杂运维面板。

### 3.2 AI Gateway

AI Gateway 负责校验和执行编排。

它统一处理：

- capability 校验。
- 模型合法性校验。
- credential source 解析。
- 额度扣减和失败退款补偿。
- provider 调用。
- 请求日志写入。
- 标准错误码返回。

所有产品线都只能通过 AI Gateway 发起正式 AI 调用，不允许直接打 provider，也不允许自己维护第二套额度和日志逻辑。

## 4. 运行时治理最小闭环

第一阶段把运行时治理收敛成四个统一对象：

### 4.1 Provider 状态

统一状态枚举：

- `enabled`
- `misconfigured`
- `disabled`
- `dry_run_only`

示例：

- `mock` 常驻 `dry_run_only`。
- `openai_compatible` 缺少必要环境变量时为 `misconfigured`。
- 后续明确关停的 provider 为 `disabled`。

账号中心和内部接口都只展示这套状态，不再各写一套模糊文案。

### 4.2 环境变量约定

环境变量不只是“代码里能读”，而是要提升为可判定的 readiness 机制。

每个 provider 需要定义：

- 最小必需配置。
- 是否允许真实调用。
- 默认支持哪些 capability。
- 是否只允许 dry run。

账号中心需要基于这层 readiness 明确显示“为什么当前不可用”，而不是等请求失败后才暴露配置问题。

### 4.3 标准错误码

第一阶段统一收口为：

- `unauthorized`
- `insufficient_credits`
- `provider_unavailable`
- `provider_misconfigured`
- `model_not_allowed`
- `capability_not_supported`
- `execution_failed`

产品 route 只负责把这些错误安全翻译给前端，不再自行定义大量散乱错误结构。

### 4.4 请求日志

请求日志继续坚持“可审计但不泄密”。

保留字段：

- capability
- modelId
- providerId
- credentialSource
- productSlug
- toolSlug
- creditCost
- status
- errorCode
- inputSummary
- outputSummary
- createdAt

默认不长期保留：

- 完整 prompt
- 原始图片
- 原文全文
- 用户 key

这样账号中心能看趋势，平台能查问题，同时避免把日志变成高风险数据池。

## 5. 账号中心 AI 治理面

第一阶段建议把账号中心 AI 治理面收敛成四个区块，不继续扩散成更多占位页。

### 5.1 能力与模型目录

回答“我能用什么”。

展示内容：

- capability
- 当前可用模型
- 推荐模型
- 单次积分消耗
- 支持的 credential source

这里不是模型市场，而是能力目录和费用解释层。

### 5.2 运行时状态

回答“平台现在稳不稳”。

展示内容：

- provider 当前状态
- 是否仅 dry run
- 是否缺少环境变量
- 当前支持哪些 capability

第一阶段不做复杂健康检查，只做静态 readiness 和配置状态判断。

### 5.3 最近请求记录

回答“最近发生了什么”。

展示内容：

- capability
- 模型
- 产品来源
- 积分消耗
- 成功 / 失败状态
- 失败原因大类

第一阶段只做最小筛选：

- 全部
- 成功
- 失败

不急着上分页、全文搜索和高级过滤。

### 5.4 最近积分账本

回答“为什么积分变了”。

它继续和请求记录并列展示，确保用户能从语义上把某次调用和某笔账本对上，减少“是不是扣多了”的疑问。

第一阶段不放入账号中心治理面的内容：

- 真正可编辑的 provider 配置台。
- 用户自配模型管理。
- 告警中心、失败重试和批量任务面板。
- 复杂订阅、支付和预算规则页。

## 6. 产品接线准入标准

以后所有 AI 产品线都使用同一张准入清单，满足后才算正式接入平台治理。

### 6.1 能力先注册，再接产品

产品能力必须先映射到统一 capability，例如：

- `text_generation`
- `structured_extraction`
- `image_edit`
- `ocr`

不能先写一个产品私有路由直调模型，再回头补平台层。

### 6.2 前端只能选当前能力可用模型

产品页如果允许选模型，只能从 capability-specific model list 读取，不允许自己写死模型名。

即使第一阶段不开放用户切换，服务端仍然必须按统一目录校验。

### 6.3 调用必须经过 AI Gateway

产品 route 只能调用平台 Gateway，不允许直接打 provider，也不允许自己维护第二套扣费、日志和错误码逻辑。

### 6.4 错误必须可翻译

产品至少要能稳定翻译这些错误：

- 未登录
- 积分不足
- provider 未就绪
- 模型不可用
- 执行失败

不能再统一显示为“请稍后再试”。

### 6.5 调用必须可审计

每条正式 AI 产品链路都要能在请求日志里看到：

- 来自哪个产品
- 来自哪个工具
- 使用什么 capability
- 使用什么模型
- 扣了多少积分
- 成功还是失败

### 6.6 结果必须有最小回退

如果模型返回不完整，产品自身要有最小可用回退策略，不能把空结果直接抛给用户。

TimePick URL 识别回退到 hostname 是第一条已验证样板。

## 7. 三条产品线的接线顺序

### 7.1 TimePick

TimePick 继续保留现有两条接线成果，但从这份路线开始，它只作为平级产品，不再继续占据平台治理优先级。

平台后续只做必要跟进，不再把整体节奏绑定到 TimePick。

### 7.2 PDF 工具箱

PDF 工具箱是站内第一条重点 AI 产品线。

推荐先接治理友好的能力，而不是一上来做复杂的“完整 AI PDF 平台”：

- PDF 文本摘要
- 页级翻译
- OCR 后的文本整理

建议先从 `text_generation` 或 `ocr + text_generation` 组合切入，保持输入输出清楚、易审计、易扣费。

### 7.3 AI 修图

AI 修图用户感知最强，但运行时复杂度也最高：

- 更依赖图片 provider
- 更容易涉及异步处理
- 更需要失败重试和结果预览

因此不建议它成为第一条站内主接线。治理底座稳定后，再按统一能力接入。
