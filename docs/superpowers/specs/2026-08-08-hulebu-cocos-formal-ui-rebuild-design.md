# 胡了卜 Cocos 正式 UI 参考图重制设计

## 1. 背景与问题

当前仓库中的 v1-v6 UI 资源包主要由切图、诊断版本和候选组件组成。它们可以证明资源管线可行，但还没有形成一套可直接进入正式 Cocos 游戏的视觉系统：主场景缺少统一的整体材质，控件的尺寸和文字基线不一致，普通/按下/禁用状态没有统一规则，部分资源仍是预览性质或依赖运行时程序化拼接。

本设计以用户提供的胡了卜参考图为唯一视觉基准，目标是重新建立一套固定 `390×844` 竖屏、可拆分、可接入 Cocos 的正式 UI 资源系统。参考图用于约束构图、主色、材质、信息层级和控件关系；运行时仍必须使用独立节点和真实 SpriteFrame，不能把整张参考图当成不可交互背景。

## 2. 目标

- 形成一套主场景皮肤、局内 HUD、动作/工具按钮、牌槽/牌河、弹窗和奖励卡的统一视觉语言。
- 让所有可点击控件拥有独立资源和普通/按下/禁用状态。
- 统一资源像素尺寸、透明边界、锚点、命名和 manifest，能够被 Cocos Prefab 稳定消费。
- 在 `390×844` Cocos production 包中完成主场景、牌山、HUD、手槽、动作栏、工具栏和弹窗的视觉接入。
- 保留玩法、App Flow、存档和 Coordinator 边界，不用 UI 资源重写规则逻辑。

## 3. 非目标

- 不制作横屏适配或其他分辨率的独立排版。
- 不同时制作四套完整风场主场景；第一阶段只交付青绿主场景，风场以卡片模板表达。
- 不修改 M2 App Flow、GameSession、存档协议、玩法数值、音频系统或微信小游戏 SDK。
- 不把整张参考图作为一个无法独立交互的运行时画面。
- 不承诺最终商业级动画、三首 BGM 或完整音效库；动效只保留控件状态所需的最小反馈。

## 4. 设计方向

### 4.1 混合交付方式

采用“整屏主场景皮肤 + 模块化控件 + 独立内容卡片”的混合方式：

- 背景层负责参考图里的青绿桌面、云纹、花枝、灯饰、边框和安全区。
- 控件层负责牌匾、计数器、牌河、手槽、动作按钮和工具按钮。
- 内容层负责奖励卡、风场卡、教学卡、多候选、设置、暂停和结算弹窗。

这样可以保留参考图的整体氛围，同时让状态、点击区域和文本保持真实可控。

### 4.2 视觉基线

- 主色：青绿玉石/漆面、暖米色牌面、深木托盘、低饱和金色边线。
- 反馈色：按下态使用暖橙火焰与金色高光；禁用态降低亮度和饱和度，不改几何边界。
- 材质：背景有轻微云纹和植物装饰，控件使用克制的金线、内阴影和暖色纸面；避免纯色矩形和默认 CSS 渐变感。
- 中文字形：使用可授权字体或已栅格化字形；生成脚本必须记录字形来源，禁止把不可追溯的系统字体当最终资产。
- 构图：主牌山位于中部，信息区位于顶部，工具列位于右侧，牌河/手槽位于下部，动作栏位于最底部，遵循参考图的相对比例。
- 画布：设计基准为 `390×844`，运行时只允许等比缩放和安全边距，不重新排列交互区域。

## 6. 资源技术规范

- PNG 使用 RGBA，透明边界经过 alpha 检查，不包含无意义的大面积透明画布。
- 每个资源在 manifest 中记录 `key`、`path`、`width`、`height`、`anchor`、`state` 和 `nineSlice` 信息。
- 同一控件的三态资源必须保持相同画布尺寸、锚点和可点击几何范围。
- 牌面资源使用统一牌体尺寸和符号基线；槽内牌和牌山牌只通过 Prefab 缩放，不另做第二套牌面图。
- 生成脚本输出到版本化目录，不写入 Cocos `library/`、`temp/` 或 `build/`。
- 交付目录不得包含 `.DS_Store`、`__pycache__`、调试截图和中间缓存。

## 7. Cocos 接入设计

### 7.1 SpriteFrame 映射

Cocos 通过 manifest 建立语义映射：

```ts
type FormalUiKey =
  | "hud.levelBadge"
  | "hud.scoreBadge"
  | "hud.tileCounter"
  | "board.discardSlots"
  | "board.handSlots"
  | "actions.chi.normal"
  | "actions.chi.active"
  | "actions.chi.disabled"
  | "tools.shuffle.normal"
  | "tools.shuffle.active"
  | "tools.shuffle.disabled"
  | "cards.reward.combo"
  | "modals.tutorial"
  | "tiles.mahjong.bamboo.01";
```

Binder 只消费 `FormalUiKey` 和语义状态，不按文件路径拼接，也不在运行时推断素材版本。

### 7.2 节点边界

- `SceneBackgroundArt`：只显示主场景皮肤和安全区。
- `HudBinder`：只绑定牌匾、分数、计数器和工具按钮状态。
- `BoardLayerBinder`：只绑定牌山和遮挡态牌面。
- `SlotLayerBinder`：只绑定牌河、手槽和槽内牌面。
- `ComboBarBinder`：只绑定动作按钮三态和输入锁。
- `ModalPresenter`：只控制教学、奖励、多候选、设置、暂停和结算弹窗的显示与点击回传。

任何 Binder 不得直接修改玩法状态、读写存档或计算组合。

## 8. 生成与验收流程

1. 先生成视觉 token、主场景皮肤和控件草图。
2. 输出第一版透明资源、manifest 和预览板。
3. 进行尺寸、alpha、命名、状态对齐和临时文件扫描。
4. 由 Lee 审阅第一版样稿；不通过则只修改资源生成脚本和 token，不接入 Cocos。
5. 通过后导入 Cocos，建立 SpriteFrame 映射和最小 Prefab 接线。
6. 在 `390×844` production 包中验证画面、点击层、状态切换和控制台。
7. 记录截图、构建 ID、资源 manifest 摘要和遗留问题。

## 9. 验收标准

### 视觉

- 主色、材质、构图和信息层级与参考图一致。
- 不再出现零散拼贴、金边比例漂移、按钮文字基线不齐和普通/按下态跳位。
- 主场景、HUD、牌山、手槽、动作栏、工具栏和弹窗在同一套 token 下成立。

### 工程

- 资源 manifest 完整且无重复 key；无临时文件进入交付目录。
- Cocos 能在不修改玩法规则的情况下加载正式 SpriteFrame。
- `390×844` production 包中所有可见控件位置稳定，视觉层与命中层对齐。
- 浏览器控制台无未处理异常；资源缺失时有可读的诊断日志。

### 交付

- 第一版样稿通过 Lee 视觉审阅后，才进入 Cocos 接入批次。
- 每个批次拥有独立任务、领取记录、验证命令和提交。
- 规格与后续计划不得出现英文占位符、模糊占位或未定义资源 key。

- Batch C：奖励、教学、多候选、暂停、设置和结算弹窗。
