# 胡了卜特殊事件池扩容设计稿

- 日期：2026-06-16
- 任务：T178
- 状态：进行中

## 1. 目标

把特殊事件从“少量固定关前弹窗”升级为能够承接主线后半段、高阶和构筑路线的第二版事件池。T178 完成后，事件应至少体现稀有度、风险层次、构筑联动和高阶专属差异。

## 2. 范围

本任务只做特殊事件池第二版：

- 建立事件稀有度和类型标签。
- 扩普通 run 事件池，覆盖稳收益、风险换高奖和 build 联动三类事件。
- 扩高阶事件池，给高阶 run 更明确的专属事件和奖励品质。
- 在局内状态栏/HUD 中强化事件结果文案。
- 在外层结算中保留最近事件摘要。

不做成就图鉴扩容、无尽/每日深度化、路线奖励和局外能力深化、Cocos 追平、音乐、美术、排行榜、付费或广告。

## 3. 事件结构

事件第二版由四层组成：

- 稀有度层
  - `common`：稳妥收益，帮助玩家补铜钱、补工具、补容错。
  - `rare`：主动承受一个小压力，换更高奖励品质或构筑推进。
  - `elite`：明显偏 build 或高阶风险，提供更强路线承接。
- 类型层
  - `economy`：铜钱、护符、工具、备用槽、牌河等资源类收益。
  - `risk`：下一关附加词缀、限制工具、压缩容错等换高奖事件。
  - `build`：顺着 `吃 / 碰 / 杠 / 胡 / 稳手 / 河控 / 牌尾 / 封盘` 等路线继续加深。
  - `ascension`：只在高阶 run 出现，服务高阶构筑与更高压力。
- 联动层
  - 事件可标记一到多个 build tag。
  - 当前 run 已识别构筑或已选奖励方向，会影响事件抽取顺序和说明文案。
- 结果层
  - 选择结果继续落到现有 effect 和 modifier 体系，不新增复杂新系统。
  - 重点是把“事件为何适合当前 build、风险是什么、换来的品质是什么”说清楚。

## 4. 数据流

- HTML 原型负责：
  - 维护第二版事件常量和挑选逻辑。
  - 根据当前模式、关卡、高阶档位、build profile 和已见事件，返回本轮事件。
  - 在事件面板、HUD 和状态栏中显示稀有度、类型和 build 提示。
- Web 壳层负责：
  - 继续接收 iframe 结算消息。
  - 在最近结算/最近一轮信息中展示最近事件摘要，不新增完整事件图鉴。

## 5. 设计约束

- 负面事件必须仍然来自玩家选择，不能无预警硬塞。
- 高阶事件不套普通教程节奏，只在高阶 run 里做更明确的风险换高奖。
- 第二版尽量复用已有 effect：`coins / tool / comboBonus / shield / reserve / river / modifier`。
- 不在 T178 引入新的长期存档字段，避免和后续成就/图鉴任务耦合。

## 6. 测试

- `apps/web` 测试锁定：
  - 外层壳仍发布静态 demo，并能看到第二版事件相关文案。
  - 最近结算/最近事件摘要包含事件稀有度、高阶事件或 build 联动文本。
- `packages/shared` 文本测试锁定：
  - HTML 原型包含 `SPECIAL_EVENT_RARITIES`、`SPECIAL_EVENT_TAGS`、`EVENT_BUILD_LINKS`。
  - HTML 原型包含新的高阶事件池或稀有度选择函数。
  - HTML 原型包含第二版事件文案和 build/high-ascension 提示。

## 7. 风险控制

- 先把第二版事件维持在 HTML 原型和 Web 壳层里，不抽到共享配置，避免 Cocos 追平前频繁改共享数据面。
- 不重做奖励系统，只通过事件说明和现有 reward quality 文案增加“值不值得冒险”的感受。
- 不把事件扩成完整图鉴，避免和 T179 成就图鉴扩容范围重叠。
