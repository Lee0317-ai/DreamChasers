# 麻将 Roguelike 最小可玩闭环和 MVP 开发拆分计划

**版本**：构建计划 v0.1  
**日期**：2026-05-23  
**关联任务**：T043  
**前置文档**：`MVP_VALIDATION_PLAN.md`  
**用途**：承接玩法验证计划，明确先做什么原型、验证什么结果、验证通过后如何拆正式 MVP。

## 1. 核心结论

后续不要直接开做完整 20 关、无尽、高阶周目和每日牌局。推荐按三段走：

```text
最小可玩闭环 -> 内部玩法验证 -> 正式 MVP 开发拆分
```

这三段的边界不同：

| 阶段 | 目标 | 产物 | 不追求 |
| --- | --- | --- | --- |
| 最小可玩闭环 | 让人能真实点牌、入槽、手动消除、过关、失败 | 3-5 个验证场景或 5 关以内原型 | 完整工程、完整美术、完整数值 |
| 内部玩法验证 | 判断手动吃碰杠和槽位压力是否成立 | 观察记录、问题清单、冻结/回退决策 | 大量内容堆叠 |
| 正式 MVP | 做出可上线试玩的第一版 | 规则模型、Cocos 核心场景、10 关、10 奖励、基础升级 | 无尽、每日、高阶、排行榜 |

一句话：**先证明核心玩法有感觉，再做可发布版本。**

## 2. 验证闭环的最小功能

验证原型只做玩家能感知到的核心链路，不做长期系统。

### 2.1 必须做

| 模块 | 内容 | 验证点 |
| --- | --- | --- |
| 牌山 | 2-4 层堆叠，后续可扩展，不限制死为 4 层 | 玩家是否理解“上层覆盖下层” |
| 点击 | 未被上层覆盖的牌可点击 | 可点击判断是否直觉 |
| 入槽 | 点击后进入主槽，动画期间锁输入 | 是否避免误触和状态混乱 |
| 主槽 | 默认 7 格，满槽先检测组合 | 槽位压力是否成立 |
| 组合检测 | 输出 `吃 / 碰 / 杠` 候选 | 玩家是否看懂按钮为什么亮 |
| 组合发动 | 玩家点按钮后手动消除 | 手动发动是否比自动消除更有麻将感 |
| 候选选择 | 同类多组合时可选一组 | 多组合是否真的形成策略 |
| 余牌 | 顶部显示花色剩余，必要时展开点数 | 玩家是否会用信息做判断 |
| 局内积分 | 吃碰杠获得积分 | 动作收益是否能被感知 |
| 奖励选择 | 过关后 3 选 1 | 玩家是否期待下一关变化 |
| 失败救场 | 满槽后按顺序救场或失败 | 玩家是否觉得失败公平 |

### 2.2 可以先做得很轻

- 美术可先用麻将牌占位图或简单牌面，不必最终 UI。
- 音效可只放点击、入槽、吃碰杠、失败 4 类反馈。
- 奖励可以只做 6-8 个，不必一次做满 10 个。
- 关卡可以只做 5 个以内，但必须覆盖单组合、多组合、危局、余牌、奖励。
- 局外升级只需要做表现闭环：通关获得铜钱，回到升级页看到主槽/备用槽/护符入口，不必跑完整数值。

### 2.3 不做

- 不做完整 20 关。
- 不做无尽牌山。
- 不做高阶周目、词缀、Boss 试炼。
- 不做每日牌局。
- 不做排行榜。
- 不做完整成就系统。
- 不做复杂胡牌和番型。
- 不做付费、广告、登录、云存档。

## 3. 验证原型推荐结构

验证原型建议先做 5 个小场景，而不是做 20 关。

| 场景 | 牌局重点 | 必须出现 |
| --- | --- | --- |
| 1. 入门场 | 点牌、入槽、单一 `碰` | 1 个明显三张相同 |
| 2. 顺子场 | `吃` 的识别 | 1 个同花色连续三张 |
| 3. 杠冲突场 | `碰` 和 `杠` 冲突 | 4 张相同牌，玩家可先碰或等杠 |
| 4. 多组合场 | `吃 / 碰` 同时可用 | 候选区和按钮同时点亮 |
| 5. 危局场 | 满槽救场和失败 | 主槽接近满，存在一次可救和一次不可救 |

如果内部测试者仍然看不懂第 1-2 场，暂时不要继续做奖励和升级，先改按钮、候选区和引导。

## 4. 随机牌局口径

用户已经确认牌局需要随机，但必须满足可消除规则。这里采用“受控随机”，不是完全随机。

### 4.1 组合包生成

牌局先由组合包构成，再打散进入牌山。

| 包类型 | 内容 | 作用 |
| --- | --- | --- |
| `chi_pack` | 同花色连续 3 张 | 提供吃 |
| `peng_pack` | 同花色同点数 3 张 | 提供碰 |
| `gang_pack` | 同花色同点数 4 张 | 提供杠 |
| `bait_pack` | 1-2 张相关干扰牌 | 制造误判和等待 |
| `rescue_pack` | 可补孤张的牌 | 防止死局过早出现 |
| `goal_pack` | 关卡目标所需牌 | 服务指定目标 |

验证原型只需要 `chi_pack`、`peng_pack`、`gang_pack` 和少量 `bait_pack`。

### 4.2 可解性底线

第一版生成器只保证：

```text
初始牌局至少存在一条可解路径。
```

不保证玩家任意操作都能通关。玩家提前碰掉杠牌、破坏顺子、把孤张压进主槽，都可能把局势变难。这正是策略来源。

### 4.3 杠被碰后的孤张处理

如果 4 张相同牌本来可以杠，玩家选择碰掉 3 张，会留下 1 张孤张。原型要验证这件事是否“有策略”而不是“像 bug”。

可用处理方式按优先级：

1. 后续牌山里保留补牌机会。
2. 局内奖励提供孤张转化或弃牌。
3. 备用槽自动收纳。
4. 满槽护符优先处理内部死孤张。
5. 验证关卡允许少量孤张豁免。

原型阶段不要直接把孤张标在牌面上，仍通过 `余牌` 和候选变化让玩家判断。

## 5. 验证观察和记录

验证原型要记录的不只是输赢，而是玩家有没有理解玩法。

| 观察项 | 记录方式 | 通过信号 |
| --- | --- | --- |
| 按钮理解 | 第一次按钮亮起后是否点击正确 | 不需要解释就能发动 |
| 多组合选择 | 是否查看候选再点按钮 | 会停顿并比较 |
| 槽位压力 | 是否在满槽前停下来思考 | 不再只是连续乱点 |
| 余牌使用 | 是否主动查看或根据余牌改策略 | 会说“这张后面还有/没有” |
| 奖励选择 | 是否按当前局势选奖励 | 不只选看起来数值最大的 |
| 失败公平感 | 失败后是否理解原因 | 能说出哪里点错或哪里缺救场 |

建议每次测试后记录：

```text
测试者：
测试场景：
最困惑的 1 个点：
最有趣的 1 个点：
是否愿意再开一局：
需要立刻调整的规则/UI：
```

## 6. 正式 MVP 开发拆分

验证通过后，再进入正式 MVP。正式 MVP 不等于最终形态，而是可上线试玩的第一版。

### 6.1 M1：规则模型

目标：先把规则从表现层里抽出来。

范围：

- 牌数据结构。
- 遮挡关系和可点击判断。
- 主槽、备用槽、入槽状态。
- `吃 / 碰 / 杠` 候选检测。
- 候选选择和执行。
- 余牌计数。
- 满槽救场顺序。
- 局内积分结算。

验收：

- `吃 / 碰 / 杠 / 非法组合` 测试通过。
- 主槽满时有组合不失败。
- 主槽满时无组合会进入救场流程。
- 余牌计数随消除减少。

### 6.2 M2：配置和生成器

目标：关卡和奖励配置化，避免写死在场景里。

范围：

- `tiles` 牌定义。
- `levels` 关卡配置。
- `comboPacks` 组合包配置。
- `rewards` 局内奖励配置。
- `upgrades` 局外升级配置。
- `seed` 随机种子。

验收：

- 相同 seed 生成相同牌局。
- 每关能指定组合包比例、层数、花色范围和槽位数。
- 初始至少保证一条可解路径。

### 6.3 M3：Cocos 核心场景

目标：形成正式小游戏工程主线。

范围：

- 牌山渲染。
- 点击和入槽动画。
- 主槽和备用槽 UI。
- 组合候选区。
- `吃 / 碰 / 杠` 三按钮。
- 余牌顶部面板。
- 通关、失败和奖励选择界面。

验收：

- 桌面和移动端都可操作。
- 点击、入槽、消除、失败流程无明显状态错乱。
- 牌面文字和按钮不溢出。
- 输入锁定期间无法继续点击。

### 6.4 M4：首批内容

目标：补齐可试玩内容量。

建议第一版内容：

| 类型 | 数量 | 备注 |
| --- | --- | --- |
| 验证/新手场景 | 5 | 由原型沉淀而来 |
| 正式关卡 | 10 | 先不做满 20 |
| 局内奖励 | 10 | 按吃流、碰流、杠流、槽位流、信息流分布 |
| 基础道具 | 3 | 洗牌、撤回、透视 |
| 局外升级 | 3 | 主槽容量、备用槽、满槽护符 |

验收：

- 新玩家能从第 1 关玩到第 5 关。
- 有至少 2 条明显构筑路线。
- 失败后能回到局外升级页。

### 6.5 M5：站内试玩接入

目标：让游戏站可以访问和试玩。

范围：

- Web 导出。
- iframe 或模块嵌入壳。
- 游戏开始、关卡完成、失败、奖励选择事件。
- 移动端尺寸适配。

验收：

- 游戏详情页可进入试玩。
- 基础事件能被站点接收。
- 移动端首屏不被导航遮挡。

## 7. MVP 内容冻结线

验证通过后，正式 MVP 先冻结这些：

| 系统 | MVP 内容 |
| --- | --- |
| 牌 | `万 / 条 / 筒`，每类 1-9 点 |
| 组合 | 手动 `吃 / 碰 / 杠` |
| 槽位 | 主槽、备用槽、满槽护符 |
| 信息 | 顶部 `余牌`，可展开点数 |
| 道具 | 洗牌、撤回、透视 |
| 收益 | 局内积分、铜钱 |
| 成长 | 主槽容量、备用槽、满槽护符 |
| 内容 | 10 关、10 奖励 |
| 工程 | Cocos 正式主线，Web 导出试玩 |

后置内容：

- 20 关完整主线。
- 无尽牌山。
- 高阶周目。
- 每日牌局。
- 成就图鉴完整版。
- 排行榜。
- 复杂番型和完整胡牌。
- 付费、广告、登录、云存档。

## 8. 决策门槛

验证不是走形式。每个关键假设都要有继续、调整或回退结论。

| 问题 | 继续条件 | 不满足时 |
| --- | --- | --- |
| 手动吃碰杠是否好懂 | 多数测试者能主动点击亮起按钮 | 简化候选展示，减少同时点亮类型 |
| 多组合是否有趣 | 玩家愿意比较候选 | 先只保留候选选择，不开放手动选牌挑战 |
| 槽位压力是否合理 | 玩家觉得紧张但不是无解 | 调整槽位数、牌山密度和救场顺序 |
| 余牌是否有价值 | 玩家会用余牌判断孤张和等牌 | 改成更醒目的简版，或延后展开点数 |
| 奖励是否改变打法 | 玩家会按局势选不同奖励 | 重写为路线型奖励，减少纯数值 |
| 失败是否公平 | 玩家能理解失败原因 | 增强危局提示和失败回放提示 |

## 9. 下一步执行建议

### 9.1 如果继续规划

先讨论 3 个问题：

1. 验证原型用轻量 Web/Canvas 还是直接 Cocos。
2. 候选组合区放在槽位上方，还是点击按钮后展开在按钮上方。
3. 原型先做 5 场景，还是先做 3 场景加一个奖励选择闭环。

### 9.2 如果开始实现

建议新增任务不要直接复用 T017，而是先拆一个前置任务：

```text
T044：麻将 Roguelike 最小可玩验证原型
```

推荐范围：

- `docs/modules/mahjong-roguelike/**`
- `apps/game/mahjong-roguelike/**` 或 `apps/game/gdevelop/mahjong-roguelike-prototype/**`
- 必要时只加极少量共享配置，不先动完整 `packages/shared` 规则模型。

等验证通过后，再回到 T017 做正式 MVP 的规则模型和 Cocos 主工程。

## 10. 团队评审清单

- 验证原型是否允许先用非最终 UI。
- 第一个原型是否只做 5 个场景。
- 是否同意 MVP 第一版先做 10 关，而不是直接 20 关。
- 是否同意先不做每日、无尽、高阶和排行榜。
- 是否同意局外升级第一版只做 3 个。
- 是否同意组合包受控随机作为牌局生成主线。
- 是否需要在原型里就加入体力消耗，还是先只在文档里保留。
