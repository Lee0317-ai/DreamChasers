# 麻将 Roguelike MVP 玩法验证计划

**版本**：验证稿 v0.1  
**日期**：2026-05-23  
**关联任务**：T042  
**用途**：在正式开发前，先验证核心玩法假设是否成立，并冻结第一版 MVP 边界。

## 1. 验证目的

这不是继续扩玩法的文档，而是用最小闭环回答一个问题：

**麻将 Roguelike 的核心体验，是否真的好玩、好懂、值得做下去。**

需要先验证的不是功能数量，而是这几个核心判断：

- 玩家能不能看懂 `点牌 -> 入槽 -> 等按钮亮 -> 手动发动组合`。
- 槽位压力会不会自然制造策略，而不是单纯制造烦躁。
- `吃 / 碰 / 杠` 的按钮和候选组合是否清晰。
- `余牌` 是否真的帮助决策，而不是只是一块装饰信息。
- 过关奖励是否能让玩家感觉“这局和上局不一样”。
- 救场机制是否让失败显得公平，而不是莫名其妙。

## 2. 核心假设

| 假设 | 要验证的点 | 失败信号 |
| --- | --- | --- |
| H1 | 手动 `吃 / 碰 / 杠` 比自动消除更有麻将味 | 玩家一直等系统自动消除，或完全不理解按钮含义 |
| H2 | 槽位压力能产生决策 | 玩家只是乱点，不会停下来思考保留哪张牌 |
| H3 | 多组合选择能形成策略分歧 | 玩家看见多个候选时没有选择欲望，只想“让系统替我选” |
| H4 | `余牌` 信息有用 | 玩家看不到余牌，依然能稳定做出判断，说明信息层价值太低 |
| H5 | 局内奖励能改变本轮打法 | 奖励只被当成数值加成，没有形成构筑方向 |
| H6 | 失败前救场是公平的 | 玩家觉得“差一格也能救回来”是合理，而不是拖沓 |

## 3. 最小验证闭环

验证版本只需要一个最小可玩闭环，不需要 20 关完整内容。

```text
选牌 -> 入槽 -> 候选按钮点亮 -> 玩家手动选择组合 -> 消除 -> 过关奖励
     -> 槽位压力上升 -> 救场/失败 -> 局外升级反馈
```

建议只验证 3 个关卡层次：

1. 教学层：只验证点击和入槽。
2. 决策层：出现多组合，验证玩家是否会选。
3. 压力层：接近满槽，验证救场和失败公平性。

## 4. 验证样本

建议先用 3 到 5 名内部测试者做第一轮验证。

| 样本类型 | 重点观察 |
| --- | --- |
| 没玩过这个项目的人 | 能不能看懂按钮和候选 |
| 熟悉休闲消除的人 | 会不会自然理解槽位压力 |
| 熟悉麻将的人 | 会不会主动拿麻将经验去做判断 |
| 对策略不敏感的人 | 会不会觉得信息太多、操作太重 |

## 5. 验证场景

### 场景 1：单一组合

- 目标：验证按钮是否好懂。
- 设计：只给一个明显可消除组合。
- 观察：玩家会不会等提示、会不会点错、会不会问“为什么这个能点”。

### 场景 2：多组合冲突

- 目标：验证玩家是否会主动比较 `吃 / 碰 / 杠`。
- 设计：同一批槽牌同时存在两种或三种组合。
- 观察：玩家是否愿意自己选，而不是只想要系统推荐最优解。

### 场景 3：满槽危局

- 目标：验证压力和救场顺序。
- 设计：主槽接近满格，存在和不存在组合各一次。
- 观察：玩家是否能理解“先消除，再救场，再失败”的顺序。

### 场景 4：余牌决策

- 目标：验证 `余牌` 是否真的有价值。
- 设计：一张孤牌附近，余牌面板显示相关花色很少。
- 观察：玩家是否会因此放弃某条路线，或决定换打法。

### 场景 5：奖励选择

- 目标：验证 3 选 1 是否能改变本轮构筑。
- 设计：给三种明显不同的奖励，不给纯数值重复项。
- 观察：玩家是否会基于当前局势做选择，而不是只看哪个最“大”。

## 6. 观察指标

### 定性指标

- 玩家能不能在 1 分钟内复述核心循环。
- 玩家会不会主动问 `余牌`、`护符`、`备用槽` 的用途。
- 玩家是否觉得“这是麻将味，不是单纯三消换皮”。
- 玩家是否愿意因为奖励不同再开一局。

### 定量指标

- 首局是否能在无额外讲解下看懂按钮状态。
- 是否能在第一次出现多组合时做出选择。
- 是否会在满槽前主动停下来思考。
- 是否会在过关后主动看奖励，而不是直接跳过。

## 7. 通过标准

如果满足以下条件，说明玩法方向可以继续推进：

- 多数测试者能在一轮后说清楚基础循环。
- 多组合场景能引发真实选择，而不是统一点最直观的按钮。
- `余牌` 在决策中被实际使用，而不是只被看一眼。
- 槽位压力会带来停顿和取舍，而不是纯粹乱点。
- 奖励会改变下一关的决策方式。
- 救场机制不会被误认为“系统帮忙作弊”。

## 8. 不通过时的调整方向

- 如果按钮不懂，先简化按钮文案和高亮规则。
- 如果多组合不成立，先减少候选类型，只保留最直观的两种。
- 如果余牌没用，先减少展示维度，只保留花色总数。
- 如果槽位压力太重，先放宽初始槽位或降低牌山密度。
- 如果奖励没区别，先把奖励改成路线型，而不是纯数值型。

## 9. MVP 冻结线

验证通过后，第一版 MVP 冻结以下内容：

- 只保留 `万 / 条 / 筒`。
- 只保留手动 `吃 / 碰 / 杠`。
- 主槽、备用槽、满槽护符、局内积分、铜钱、余牌。
- 3 个基础道具：洗牌、撤回、透视。
- 10 个可玩关卡先行验证。
- 10 个局内奖励。
- 3 个局外升级：主槽容量、备用槽、满槽护符。

验证前先不冻结这些内容：

- 20 关完整节奏。
- 每日牌局。
- 无尽牌山。
- 高阶周目。
- 排行榜。
- 复杂成就。
- 完整胡牌和复杂番型。

## 10. 验证结束后的出口

- **如果通过**：进入正式开发计划拆分，优先做规则模型、关卡配置和 Cocos 核心场景。
- **如果不通过**：回到 `H1-H6` 中最弱的一条，做一次局部修正后再测。

## 11. 团队评审问题

1. 玩家是否真的愿意手动选 `吃 / 碰 / 杠`。
2. 多组合候选是否要在槽位附近直接展示。
3. `余牌` 应该默认简版还是一开始就展开。
4. 10 关验证是否足够，还是需要 5 关先跑通。
5. MVP 是否应该先冻结奖励，再冻结关卡。
6. 失败前救场是否要在第一版就完全可见。
